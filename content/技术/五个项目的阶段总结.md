最近，我把几个方向不同的项目放在一起重新梳理：伴行 WalkWith、InfraPilot、VisionLint Local、Lexora，以及 ReasonTrace。它们涉及无障碍交互、信息化工程、网页质量检查、英语学习和数学推理，但都在尝试把一个具体问题变成可以解释、可以验证、可以继续维护的工具。

这是一份阶段记录。以下内容以 **2026 年 10 月 14 日可核对的本地代码、产品规格和交接文档**为依据；设计方案、已有实现和历史验证分别表述。本地工作树中的功能不一定都已同步到公开仓库，也不代表已经完成生产交付。

## 五个项目分别在解决什么问题

| 项目             | 核心问题                                                       | 当前可确认的阶段                                                               |
| ---------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 伴行 WalkWith    | 如何帮助有沟通、视觉或行动障碍的用户完成现实生活中的任务       | Phase 0 产品规格与无障碍交互设计，尚无可运行小程序                             |
| InfraPilot       | 如何把信息化工程问题转成可复用、可检查的软件工具               | FDE 学习实践，已实现独立的 Python 工程量计算模块                               |
| VisionLint Local | 如何让网页视觉问题的发现、定位和修复复验形成闭环               | 已有本地审计 Skill、规则引擎与视觉模型接入代码；真实模型和宿主环境验证仍需确认 |

## 1. 伴行 WalkWith：先把无障碍任务设计清楚

伴行 WalkWith 的方向是微信小程序形态的多模态无障碍生活助手。产品规格覆盖听障、言语障碍、低视力、行动不便和老年用户，但当前的首要工作是收敛任务与交互范围。

原型规划了“我要沟通、我要出行、我要办事、紧急求助”四个入口，并围绕三条具体旅程展开：医院窗口沟通、寻找电梯，以及从单据信息整理出下一步操作。这样划分后，每一条旅程都有明确的开始、结果和失败处理，而不是让用户面对一组抽象的识别按钮。

**目前完成的是产品规格与开发实施蓝图。** 当前本地 README 明确说明尚未创建可运行程序，目录中也没有对应的小程序业务源码。因此，语音转写、文字转语音、OCR 和视觉辅助在这份总结中都属于待实现能力。

计划采用原生微信小程序 TypeScript、WXML、WXSS，并把模型、语音和视觉能力放在可替换的服务接口后面。先用 Mock Provider 验证任务流程，再决定真实服务的接入方式。这样可以提前检查模型失败、用户取消和权限拒绝时，基础沟通流程是否仍然成立。

这个项目的重要取舍是把可恢复的交互放在前面：用户需要能返回、重试或改用手动输入；相机和麦克风按需启用；视觉辅助的结果不能承担道路通行安全判断。

**下一步：** 在现有设计范围内实现三条最小旅程，通过微信开发者工具和实际设备验证，再逐项接入真实能力。

## 2. InfraPilot：从工程量计算开始练习交付

InfraPilot 是我的 FDE 学习实践方向。它与信息化工程工作相连接，后续希望逐步覆盖需求澄清、工具调用、知识检索、接口集成和交付验证。

但这个方向与已完成代码需要分开。目前本地的 InfraPilot 项目目录还是空的，已经可以运行的是一个独立的 **Engineering Quantity Calculator 工程量计算练习**。

它用三个文件组织一条很小的业务链路：`project_input.json` 保存输入数据，`calculator.py` 负责计算，`main.py` 读取数据、调用函数并输出 JSON。当前计算项包括网线、电源线、光纤长度和沟槽体积。

整理本文时，我运行了现有示例：22 台摄像机、平均网线长度 25 米、预留比例 15%、全 PoE、100 米光纤路由，以及长 60 米、宽 0.4 米、深 0.6 米的沟槽。输出为：

| 计算项     | 示例输出    |
| ---------- | ----------- |
| 网线长度   | 632.5 米    |
| 电源线长度 | 0 米        |
| 光纤长度   | 115 米      |
| 沟槽体积   | 14.4 立方米 |

这里使用的是教学简化规则。例如“全 PoE 时电源线为 0”只描述当前计算器的支线逻辑，不能替代实际工程中对供电、路由和拓扑的核算。

这个练习的价值在于先把业务规则放进可检查的函数，让输入数据可以替换，让结果能够复现。未来接入自然语言或 Agent 时，模型可以负责提取参数与解释结果，工程数值仍由明确的计算规则产生。

**下一步：** 完善输入类型、单位和边界校验，加入有代表性的测试样例，再逐步包装成 API 或工具接口。RAG、Agent、部署和可观测性目前仍是学习规划。

## 3. VisionLint Local：让网页检查能落到修复证据

VisionLint Local 面向本地网页的视觉与响应式审计，并以 Skill 形式对接 WorkBuddy。它希望把“看起来有问题”转成可定位、可复验的检查结果。

已有工作流把 Playwright 页面采集、截图、DOM Grounding、确定性规则和本地视觉模型串起来。规则用于识别横向溢出、文本裁剪、异常重叠、坏图及响应式问题；模型结果需要引用采集到的元素标识或选择器，才能与实际页面建立对应关系。

修复之后，通过 `verify-fix` 再次检查，并把结果区分为 `fixed`、`still_present` 或 `inconclusive`。无法判断时保留不确定状态，是这个闭环的重要部分。

实现采用 Python、Playwright 和 OpenVINO，本地视觉接入默认指向 Qwen2-VL 的 INT4 模型。短生命周期客户端访问常驻本地服务；服务中的模型管理器按模型路径和设备复用实例，减少重复加载，并暴露加载状态供诊断使用。

“本地”指的是准备好环境和模型后的推理路径。首次安装依赖和下载模型仍然需要网络，不能把它描述为完全没有外部依赖。比赛 HTTP 入口也设置了明确的失败处理：模型未准备或运行环境不可用时返回失败，不把没有完成视觉检查的结果包装成正常审计。

**当前边界：** 可以确认审计代码、测试结构、服务协议和发布脚本已经存在；这次没有重跑真实模型，也没有确认完整 WorkBuddy 实机调用和比赛发布。因此，真实环境中的稳定性仍需要后续证据。

**下一步：** 补齐 Windows、Chromium、模型与宿主调用的复现记录，用同一页面展示发现问题、修复和复验的完整过程。

## 4. Lexora：把英语学习流程留在本地

Lexora 是一个本地优先的英语学习 Web 应用。目前已有单词与句子的主动打字练习、Daily 和 Review 短会话，以及 Reader 阅读模块。

Reader 支持本地文章、查词保存、阅读进度、可选音频和文章复习包。它尝试把阅读中遇到的内容带回复习流程，减少阅读与练习之间的断点。词汇练习中的会话重试与长期复习调度也进行了区分，避免一次手动练习直接改变长期复习安排。

前端使用 React、TypeScript 和 Vite。核心学习流程加载后不依赖账号或 AI API，学习记录主要保存在当前浏览器来源下的 `localStorage` 中。这里的“本地优先”也有清楚的边界：它不等于原生离线安装，也不等于所有数据都跨设备保存；句子练习的会话进度目前只在内存中，刷新会丢失。

项目还提供可选 Node 服务，用于受限文本或字幕导入与同步。这些能力需要单独配置和授权，核心学习流程仍能独立运行。当前句子品读使用预置资料和有限的本地生成器，并保留人工审核门槛；复杂或未知句子可能无法分析，不能据此宣称已经有通用语法分析或 AI Tutor。

**当前阶段：** 主要学习与阅读流程已有本地实现，并有验收记录；部分最新工作仍在本地，本文描述的进度不等同于公开仓库已经完整同步的版本，也不代表已经证明学习效果。

**下一步：** 继续提高阅读、保存与复习之间的连贯性，完善数据备份和可恢复状态，并补上真实浏览器、输入法和设备验证。

项目仓库：[Xhwe-x/Lexora](https://github.com/Xhwe-x/Lexora)。

## 5. ReasonTrace：从定位错误到验证理解

ReasonTrace 的定位是 **Reasoning Debugger**，当前聚焦代数推导。用户提交题目、逐步推导、最终答案和自报信心后，系统先检查相邻步骤之间的变换，寻找第一个能够确认无效的步骤转换。

随后，AI 诊断可能的误解，Challenge Verifier 对诊断进行复核，再进入 Teach-back 和迁移检查：用户需要解释修正，并处理近迁移、远迁移或容易再次犯错的题目。这条流程把“得到答案”和“理解修正”分开处理。

项目使用 Next.js、TypeScript、Supabase 和服务端模型接口。确定性代数检查器负责数学变换的有效性；模型负责诊断、挑战复核和教学反馈。模型解释不会自动成为数学证明，证据合并逻辑会区分 `VERIFIED` 与 `AI_SUPPORTED` 等状态。

当前检查器有明确支持范围，包括部分单变量多项式与线性方程等价、简单线性不等式方向翻转，以及受限的零乘积和分支匹配。涉及不支持的除法、定义域变化、多变量或过多分支时，需要返回 `unsupported` 或 `ambiguous`。这种边界让结果更容易解释，也决定了它目前不是通用数学解题器。

**当前阶段：** 已有应用、公开仓库和比赛交付文档。文档中记录了单元测试、检查器评测、AI 评测和演示排练，但这些是历史记录，本次没有重新运行。固定演示流程还包含明确标注的历史结果回退机制，不能把回退展示当作实时 AI 请求成功的证据。

**下一步：** 在已有能力范围内继续完善不确定结果、失败重试和学习闭环，再用固定样例与可追溯评测决定是否扩展数学范围。

项目仓库：[Xhwe-x/reasontrace](https://github.com/Xhwe-x/reasontrace)。项目文档还列有演示地址，但这次未能确认其在线可用性。

## 这些项目带来的共同认识

### 先定义任务，再选择技术

WalkWith 的三条旅程、InfraPilot 的几项工程量、Lexora 的练习与阅读循环，都是可以先划清输入和结果的任务。范围越清楚，越容易判断一个功能究竟已经成立，还是只完成了界面和接口。

### 把可以确定的部分交给规则

工程量计算、网页规则检查和代数步骤验证，都有一部分能够通过明确规则复现。模型适合补充理解、诊断与解释，但结果还需要规则、数据和用户反馈来支撑。

这也是我在几个项目中反复遇到的设计问题：哪些判断可以确定，哪些只能给出建议，哪些信息不足时应该停止。

### 失败处理是产品流程的一部分

权限被拒绝、模型尚未加载、句子无法分析、数学变换超出支持范围，这些状态都会影响用户能否继续完成任务。返回什么信息、能否保留输入、如何重试，需要与正常流程一起设计。

### 用记录说明进度

产品蓝图、代码实现、Mock、历史测试和真实设备验收承担不同职责。复盘时把它们分开，可以更准确地说明当前进度，也能让下一步工作有明确的起点。

## 接下来如何继续推进

我会沿着各自已经明确的边界继续推进：WalkWith 先实现和验证最小旅程；InfraPilot 先完善计算模块；VisionLint 补齐真实环境的审计闭环；Lexora 继续打通学习与阅读；ReasonTrace 在已有代数范围内提高反馈与验证的一致性。

每个项目的下一次总结，都应该能够回答三个问题：新增了什么可用能力，留下了什么验证证据，还有哪些问题尚未解决。
